# Design

## Context

See [proposal.md](proposal.md) for motivation and the five capability deltas for the behavior contract. The public Next.js app exports static pages to private S3 behind CloudFront. A separate Keystatic 0.6.9 app on the Pi commits YAML and media directly to the public GitHub repository. Today English fields and `publishedAt` live at the YAML root, Portuguese is optional under `pt`, and `selectPortuguesePosts` can publish Portuguese only after English. `fields.text({ multiline: true })` preserves raw Markdown but is only a textarea. Image uploads are a separate indexed array, with manual Markdown references. The release workflow runs on every `main` push and every 15 minutes; on push, preflight always requests a deploy. An incomplete `Published` record missing `publishedAt` currently blocks preflight rather than being stopped in the CMS.

The current main OpenSpec inventory has `blog-experience` and `site-quality`, but the established `blog-authoring`, `blog-localization` and `continuous-delivery` paths still live in unsynchronized earlier changes. Those older deltas explicitly assume English-first and scheduled publication. Reconcile/synchronize them before syncing this change, with this change's final rules taking precedence; do not rewrite historical change files silently. Existing dirty operational notes in the worktree are user-owned and must be preserved.

## Goals / Non-Goals

**Goals:** Keep one static article per public language URL, one Git-backed article identity and shared media inventory, raw Markdown source, publish-time dates that do not move on edits, and safe asset delivery independent of the Pi at visitor time. Make draft saves quiet while retaining validation and recovery.

**Non-Goals:** Translate text automatically, localize the English portfolio homepage, create separate slugs, publish at a future time, switch to MDX/Markdoc/WYSIWYG, fetch arbitrary remote images, accept SVG uploads, change the S3/CloudFront architecture, or alter Overleaf resources. The CMS image updater on the Pi and the separate retention workflow are not the removed site-publication cron.

## Decisions

### 1. Separate article identity, global visibility, and language readiness

Use one record keyed by the existing path slug. Keystatic 0.6.9 requires its collection `slugField` to be a top-level slug form field, so keep a root `title` field as the slug seed/identity and store the mutable editorial payload under one root `editorial` field. For a new article, `title` starts with the Portuguese title and suggests the slug once; subsequent localized title edits are stored in `editorial.pt.title` without renaming the URL. An existing English-origin article retains its root title and path slug, while its actual English and Portuguese display titles live in the editorial payload. The reader may use the root Portuguese title when a new record has no explicit `editorial.pt.title`; a legacy English root title must never become a Portuguese fallback.

The `editorial` payload contains shared `author`, optional still `cover` and media inventory, plus `pt` and `en` versions with their own `title` override where needed, `summary`, raw Markdown `body`, tags, cover alt and publish approval. It also owns the global `Draft`/`Published` state so returning the whole article to Draft withdraws every route. New records do not contain author-editable timestamps. Legacy dates may remain as explicit migration pins, outside the editor, to preserve existing public chronology. Global Published requires at least one complete approved locale. A locale's public eligibility requires global Published, its approval, complete fields, and a resolvable first-publication instant from the production Git history or a reviewed legacy pin. The editor presents `pt` first; English remains optional. This is an internal YAML layout change only: public URLs, locale availability and reader-facing copy remain as specified.

The English home page and `/blog/` continue to consume only the English projection; `/pt/blog/` consumes only Portuguese. Search indexes, static routes, sitemap, reciprocal `hreflang`, canonical/OG/structured data, language switch, and media references all use the same eligibility predicate. There is no cross-language prose fallback. A Portuguese-only article has no English article route or card; an English translation added later can become the latest English post. The existing English-only records remain valid through a compatibility reader during rollout.

**Alternative considered:** Keep English root fields but merely reorder the form. This would still make the English title/slug field structurally mandatory and leave Portuguese dependent on an English parent. Two YAML files per language would avoid the schema migration but duplicate identity, media and withdrawal state.

### 2. Derive and preserve dates from successful production commits

The first commit on `main` containing an article establishes its immutable creation instant. The first commit on `main` in which a complete, approved language is globally Published establishes that language's immutable first-publication instant. Use the Git committer instant in UTC, not browser time, a build cutoff or the latest edit; a failed or merely local Keystatic save has no date. Later public edits expose a separate last-modification instant, while withdrawal and re-publication preserve the original first-publication instant. The date shown in each public article/card and used for ordering, search, sitemap and structured data is that language's first-publication instant. The English home feature therefore uses the newest public English instant. Legacy publication dates are preserved through reviewed migration pins rather than silently replaced by the migration commit.

The release checkout must contain full `main` history. Resolve dates from historical versions of the article using the same safe parser and eligibility rules as the current source, cache the result per build, and never interpolate author-controlled slugs into shell commands. A missing, shallow, rewritten or unparsable history for a newly published locale fails closed before release; do not synthesize a current time or expose a page without a trustworthy date. CMS preview may display a saved revision's derived date, but an unsaved draft must not claim one. Keystatic has no configured collection-level async pre-save hook and serializes local browser drafts before a GitHub commit, so timestamping inside a form serializer cannot meet the first-successful-save rule.

Prototype a top-level slug field paired with a custom compound editorial/assets field before migrating the schema: the latter must own status, approval, localized Markdown and media in one validated form state, without editable date controls. Prove that root-title/slug handling, parse/serialize, asset persistence and `onChange` preserve existing saved values, a failed save can be retried without publishing, and the editor blocks incomplete publication. Keystatic's normal GitHub save must atomically commit the record and media. If the pinned form API cannot meet those tests, stop and revisit the design before migration.

**Alternative considered:** a CMS-server clock synchronized before Save. Keystatic serializes the form into local browser drafts before a successful GitHub commit, so an attempted timestamp can survive a failed or abandoned save. A date on every build or latest commit would move after unrelated changes. A first qualifying production commit is a durable event with no manual field or corrective second commit.

### 3. Keep source Markdown and integrate media within its save

Build a small enhanced Markdown input, not a new document format. It keeps text editing, selection, paste of ordinary text, headings, fenced code and exact source round-tripping. When clipboard/drop supplies image bytes, the editor validates type/size, derives a stable local asset reference, adds the bytes to the same Keystatic save state, and inserts `![alt](/media/...)` at the current selection. Give the author a short alt-text prompt or editable placeholder; published content cannot contain a missing informative alt. The same saved reference may be reused in English with a different Markdown alt. If clipboard contains only text/HTML/URL, do not fetch remote media or invent a local reference; the file picker remains available for GIFs copied as only a static frame.

Prefer stable, content-addressed filenames for *new* inline assets rather than paths derived from an array index, because reordering an image array would otherwise break old Markdown. Keep a compatibility path for existing indexed media. Prototype the Keystatic composite/asset field at the installed version to verify it can persist Markdown and image bytes in one Git commit, including multiple pastes, retry, removal and deduplication. The protected preview remains based on the last saved Git revision and must not claim unsaved media is public. Avoid a separate upload endpoint that commits an orphaned image before the article saves.

**Alternative considered:** Keystatic's Markdoc/MDX rich fields support editor-managed images, but changing to either format would migrate both languages, complicate the current safe React Markdown renderer, and weaken the promised raw-source round trip for the sake of one editing affordance.

### 4. Add GIF as bounded, accessible body media

Extend the upload, repository-reference, preview, build/export, S3 metadata and public-route validation chain to recognize `.gif` as `image/gif`; verify actual bytes, dimensions, frame count and decoded work rather than trusting a filename or browser MIME. Proposed initial cap: 5 MiB per asset, at most 120 frames, and a conservative decoded-pixel budget; exact dimensions may be tuned after fixture tests without weakening the caps. Animated GIF is permitted in body Markdown only. The cover stays PNG/JPEG/WebP and remains optional; it currently appears in the article, not blog cards or home feature.

Generate a content-hashed still first-frame poster for each GIF. Render with reserved dimensions, lazy-load when below the fold, provide a visible Pause/Play control, and select the poster instead of downloading/playing motion by default under `prefers-reduced-motion: reduce`. Keep the raw GIF and poster under validated local media paths with appropriate MIME and immutable caching. Preview and public page use the same presentation rules. Preserve the current Markdown safety boundary: no raw HTML/MDX execution or executable external image URLs.

**Alternative considered:** Converting all GIFs to video would reduce transfer size for long animations but fails the requested GIF authoring workflow and adds format/player work. Long/heavy animations can be reconsidered separately; the initial cap deliberately favors short loops.

### 5. Make public releases event-driven and no-op aware

Remove only the site-release `schedule` trigger and `Scheduled` editorial state; retain `push` to `main` and authorized `workflow_dispatch`. A CMS save already creates a Git commit, so first publication, public edits, added translation and withdrawal use the existing event. Preserve verification, OIDC/AWS scope, serial production mutation, freshness checks, retained snapshot recovery, stale-route cleanup and CloudFront invalidation on real public changes. The Pi's CMS image updater and separate retention job remain unchanged.

Replace `push => always deploy` with a conservative public-output fingerprint in preflight. It covers the public-facing code/config inputs plus normalized eligible English/Portuguese content and referenced asset hashes. It excludes only known non-public CMS-only/operations/docs inputs and non-public editorial content; unrecognized changes default to a deploy. Store the fingerprint in release state/manifest with backward-compatible reading of old state (missing fingerprint forces one verified release). Compare content, metadata, bodies, visibility, dates and media bytes, not merely slug lists. A draft-only CMS commit still gets a concise preflight result, but no build/upload/invalidation. Manual dispatch may force a verified recovery release even if fingerprints match. Never use workflow-level cancellation that could interrupt a public mutation; stale candidates are rejected and deploys stay serialized.

**Alternative considered:** Removing cron alone would leave every draft save deploying. Filtering only by changed paths would miss withdrawal or an edit under the same slug, while comparing only eligible slug lists would miss content changes. A fingerprint is explicit and testable.

### 6. Stage migration to avoid mixed CMS/site versions

Add dual-read support for old and new YAML before writing any new-format record. The new reader consumes root `title`/path identity plus `editorial`; migration moves old top-level English fields to `editorial.en` and old `pt` fields to `editorial.pt`, preserving the original root title, slug and public URLs. It must not interpret an English-origin root title as a Portuguese translation. Preserve existing published English date/updated date as reviewed legacy pins; for already-public Portuguese, retain its currently displayed shared date rather than inventing a later publication. Derive creation from the first trustworthy production content commit when available; if legacy history is unavailable, use the earliest existing persisted publication date as a documented migration-only fallback. New records and newly published translations never receive fallback dates. A legacy `Scheduled` record already public may remain public after explicit review; a future/not-yet-public scheduled record becomes Draft pending Lucas's review, never silently public.

Roll out: compatibility reader/tests first; build and smoke-test the Portuguese-first ARM64 CMS image against migrated fixtures before touching the Pi; perform a dry-run migration with before/after public-route and content hashes. Keystatic 0.6.9 applies one collection schema and cannot safely edit the old and new YAML shapes at once. Lucas approved a short maintenance window for the dedicated editor: pause only that editor, preserve its last working image and the active S3 release state, apply the reviewed migration and switch to the new CMS image as one controlled cutover, then verify health/authentication and run the push/manual public smoke tests. Do not modify Overleaf, its tunnel, or user-owned dirty operational files. The CWES English/Portuguese publication instant remains the existing `2026-10-09T18:00:00.000Z` legacy pin; stale publication/update timestamps on the unpublished placeholder draft are dropped. If failure occurs before migration, restore the old CMS image. Once new-format records are saved, rolling back to the old English-first CMS/parser is unsafe; recover with the new compatible image or pause the editor while repairing the new-format schema, and use the existing S3 snapshot/CloudFront invalidation path for public rollback. Reconcile prior OpenSpec deltas in chronological order before syncing this change's final specs.

## Risks / Trade-offs

- [A CMS save does not expose a reliable cross-field lifecycle hook] → Prove the compound-field behavior with the pinned Keystatic version before migrating records; halt for a design revision if an atomic saved record cannot be guaranteed.
- [A checkout lacks trustworthy production history] → Fetch full `main` history for release, derive dates only from successful qualifying commits, and fail closed for new public versions rather than inventing dates.
- [Old and new article formats meet a single-schema editor] → Keep the public reader dual-read; test the new ARM64 editor against migrated fixtures before cutover, then briefly pause only the dedicated CMS while changing content and image together. Never allow the obsolete editor to save a migrated record.
- [A pasted image reference is inserted but the asset is not committed] → Treat Markdown and asset as one form transaction; reject save or retain an unsaved retry state, never publish a broken reference.
- [A GIF causes excessive CPU, transfer or motion] → Enforce byte/frame/pixel budgets, poster and pause/reduced-motion behavior, lazy loading and mobile performance tests.
- [A fingerprint misses a public input] → Exclude only known non-public paths, include all published content/media and default unknown files to deploy; test same-slug edits, withdrawals and code changes.
- [No cron means no automatic future release] → Remove the Scheduled control, explain push/manual publishing in the CMS guide, and review legacy scheduled records before conversion.
- [A published post in the public repository is invalid before migration] → Fix or return it to Draft through the normal authoring path before a production cutover; never bypass release validation or publish partial content.

## Migration Plan

1. Baseline the current public URLs, release manifest, existing content states and CMS image; verify any currently failing publication, and preserve unrelated worktree edits.
2. Introduce and test a dual-read model plus backward-compatible public projection, without changing saved records or removing cron yet.
3. Prototype and validate the Portuguese-first composite CMS editor, commit-history date resolution, image paste transaction and GIF preview in local/GitHub-mode tests; build and verify an ARM64 image against migrated fixtures without changing the running editor or Overleaf.
4. Dry-run the idempotent content migration and review scheduled records; compare public URLs, English home feature, search, sitemap and media before/after. Pause the dedicated editor for the approved short maintenance window, migrate and switch its image together, then verify health/authentication before resuming editing.
5. Enable per-locale publication and GIF output, remove the site-release cron/old status, and publish through the push-driven pipeline. Verify Portuguese-only, English-later, same-slug edit, withdrawal, draft-only no-op, reduced-motion and 404 behavior on real static export and CloudFront.
6. If public deployment fails, retain/restore the previous S3 snapshot. If CMS rollout fails before migration, revert only the dedicated CMS image. After migration, recover using a compatible parser/editor rather than restoring the obsolete schema. Reconcile and sync OpenSpec capability histories after acceptance; do not modify Overleaf.
